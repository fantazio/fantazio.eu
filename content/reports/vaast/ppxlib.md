The multi-version-compatible design of ppxlib is due to the [same observation on
the `Parsetree`](https://discuss.ocaml.org/t/the-future-of-ppx/3766) as we made
to the `Typedtree`: it breaks in between OCaml version. Their observation was in
the context of PPX, ours in the context of static analyzers. A more thorough
description of the actual design is available in [ppxlib's
documentation] (https://ocaml-ppx.github.io/ppxlib/ppxlib/compatibility.html)
<div class="alert-cite">

> One of the important issues with working with the Parsetree is that the API is not stable. [...]
>
> This instability causes a maintenance issue. PPX authors wish to maintain a single version of their PPX, not one per OCaml version, and ideally not have to update their code when seemingly irrelevant changes to the OCaml Parsetree happen.
</div>

To solve this issue, ppxlib sits between the ppx-es and the compiler.
In order to support multiple versions, ppxlib chooses a common representation
and know how to transform different Parsetree versions to this representation.
The chosen representation is actually a fixed version of the Parsetree
(currently OCaml 5.2's). This is not breakage-resilient but the selected
version remains for long enough that breakage is not frequent :
3 years have passed between selecting OCaml 4.14's Parsetree ([ppxlib
0.26.0](https://github.com/ocaml-ppx/ppxlib/releases/tag/0.26.0)),
and updating it to OCaml 5.2's ([ppxlib
0.36.0](https://github.com/ocaml-ppx/ppxlib/releases/tag/0.36.0)).\
In addition to selecting a Parsetree version, ppxlib also knows how to migrate
one Parsetree version to another. This way, one can write a ppx using ppxlib's
version but run it with a different version of the compiler (older or newer).
In this situation, ppxlib simply migrates the current compiler's Parsetree
to its frozen version, apply the ppx on it and migrate back. This design allows
ppxlib's driver to apply all ppx-es in a single traversal of the Parsetree.

In addition to selecting a Parsetree version, ppxlib offers an API to easily
build and destruct its nodes. This API offers ppxlib users more resilience
against Parsetree changes when the frozen version is bumped.\
For [builders](https://ocaml-ppx.github.io/ppxlib/ppxlib/generating-code.html)
ppxlib provides both low-level and high-level functions in `Ast_builder`.
Low-level functions are generated by translating the nodes into functions (e.g.
`pexp_constant ~loc constant` builds the expression
`{pexp_loc = loc; pexp_desc = {Pexp_constant constant}; pexp_attributes = []}`).
High-level functions are wrappers over the low-level functions that provide
a simplified API for reccurrent actions (e.g. `eint ~loc 1` instead of
`pexp_constant ~loc (Pconst_integer ("1", None))`). This high-level API remains
very stable over the years.\
The API of [destructors](https://ocaml-ppx.github.io/ppxlib/ppxlib/matching-code.html)
mirrors that of buidlers. It actually works in 2 steps: first by defining
patterns (this is the mirror), then by enacting on patterns. This is similar to
pattern matching constructs in OCaml : `pattern -> expression`. To further the
similarity, ppxlib offers some combinators that reflects regular OCaml pattern
constructs (e.g. the wildcard `_` is emulated as `drop`, and the alternative
`p1 | p2` as `alt p1 p2`).\
In addition to the functional APIs, ppxlib also offers a ppx named `Metaquot`.
This is available for both builders and destructors, and facilitates writing
them as "regular" OCaml code (e.g. `let e = [%expr 1 + 1]`).

Although the selected version is not the latest, ppxlib offers a mean to
interact with newer nodes by encoding them as extension points [as discussed in
this thread](https://discuss.ocaml.org/t/ann-ppxlib-support-for-future-compilers/17430).
The benefit of that design is that it makes ppx-es forward-compatible with new
features, while the fixed version + migration scheme takes care of a more
general compatbility with features existing in the selected version.
