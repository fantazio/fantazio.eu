The action took place from August 1 to October 31, 2026.

[LexiFi](https://www.lexifi.com/) agreed to fund the development of the
[dead_code_analyzer](https://github.com/LexiFi/dead_code_analyzer) in the
continuity of the previous
[OCSF action](https://fantazio.eu/reports/ocsf/dca_2026-02-24.html)
at a rate of 80€/h. The action focused on selected tasks which were split
into 2 priorities:
- the core tasks, estimated at 100h of work: bug fixes, and extendig the
    supported OCaml versions to multple ones, especially 5.4 and 5.5;
- additional tasks, upon statisfaction with the previous work, estimated
    at 50h of work: some code refactoring, and handling uses in first
    class modules.


Following the agreed rate of 80€/h, this amounts to 8k€ for the core tasks
and an additional 4k€ upon success for the remaining tasks, totaling 12k€
for the whole action.

The core tasks lead to
[releases 1.2.1 and 1.3.0](https://discuss.ocaml.org/t/ann-dead-code-analyzer-1-2-1-and-1-3-0/18530).

Over the action period, I spent a total of 197h on the project, of which
I invoiced 150h to LexiFi.\
The following sections break down the work funded.
They are ordered by volume of work rather than chronologically.

Overall, this results in more precise reports with fixed false positives in
the presence of includes, module types, module aliases, object aliases,
and type equivalences, and fixed false negatives in the presence of complex
factory functions.

There are two important changes introduced by the listed PRs:
- The analysis relies on `Env.t` values occasionally to resolve type
    equivalences, which incurrs a performance cost (almost 30% slower
    using `-a -T all` on Frama-C and almost 20% on Opam).
- The `cmi_infos` are not read anymore. Instead, collecting elements of
    interests is done by traversing the `Typedtree.signature` or
    `Typedtree.structure` held in a .cmt's `cmt_annot`.

This work is included in release
[1.2.1](https://github.com/LexiFi/dead_code_analyzer/releases/tag/1.2.1)

## Refactor (34h)

This work is available in
[PR #111](https://github.com/LexiFi/dead_code_analyzer/pull/111).

The goal of this refactor is to separate the identification of relevant
information in the Typedtrees from its storage.

Before this work, a lot of the storage was scattered all over the codebase,
making it hard to maintain at times. In addition, the storage was "raw",
i.e. identification code would directly manipulate the data structures
used for storage, making both the identification code harder to read and
the storage code harder to update.

Now, most of the storage is contained in a `State.t` and manipulated via
a functional API. As a result, the data structures are abstracted away and
can be updated freely, one can easily add debug logs to identify the elements
tracked, used, ..., and the storage-related noise in the
identification code is reduced.

This work is not part of any release yet.

### Future

Refactoring a codebase can be a rabbit hole. I am not surprised that
it took a little longer than planned.\
In order to limit the duration of this work, it focused on the storage related
to the main report sections of the analyzer. More work remains to apply the
same architecture to the optional arguments and stylistic issues sections.

In addition to the storage vs identification refactor, there is information
about the element being analyzed that are remembered (current module's path,
current class, ...) that could benefit from a similar refactor.

Finally, the code could use some simplification and comments in some parts to
clarify the intent and facilitate the maintenance.

I am very happy LexiFi agreed to fund this task and believe this kind of work
is too often pushed back because of its time-taking nature although it does
provide short term benfits and may provide long term benefits greater than its
cost.

## Multi-version compatibility (25h)

This work is available in
[PR #100](https://github.com/LexiFi/dead_code_analyzer/pull/100).

The analyzer used to only support one OCaml version at the time.
Release 1.0 updated the supported version to OCaml 5.2, and 1.2 to 5.3.
Those updates implied dropping support for the previous versions. As a
result, I had setup a branch dedicated to 4.14 for users that have not
moved on to OCaml 5.

Now, the analyzer supports all OCaml versions from 4.14 to 5.5. This is
a great step to improve the accessibility of the tool and the user experience.

This work went more smoothly than expected. The most complicated changes
were already handled by 1.2 when updating to OCaml 5.3.\
However, a few inconsistencies remain in the reports in between versions.
Those are tracked by the
[issue #103](https://github.com/LexiFi/dead_code_analyzer/issues/103).

The support is done via [cppo](https://github.com/ocaml-community/cppo).
Most of the version-compatibility artefacts are concentrated in a new
`Utils.Compat` module in order to limit the impact on the rest of the
codebase and ease maintenance.

This task resulted in the analyzer's release
[1.3.0](https://github.com/LexiFi/dead_code_analyzer/releases/tag/1.3.0).

### Future

I intend to address the inconsistencies and update the multi-version
support to include new OCaml releases as they come.

Although cppo does a great job at providing build-time version-dependent
code selection inline, it does not provide any safety to ensure all the
supported versions are actually handled or discarded, and makes the code
harder to maintain.\
Alternatively, [ppx_optcomp](https://github.com/janestreet/ppx_optcomp)
could have been used but it comes with similar pitfalls. Here is what
it looks like to replace cppo with ppx_optcomp:
[multi-version support using ppx_optcomp](https://github.com/fantazio/dead_code_analyzer/commit/a9f9bf4286f4aa87139cde3bc92c74c4310ecacb).\
As a result, I released [Vaast](https://discuss.ocaml.org/t/ann-vaast-0-0-0-design-discussion/18583)
with the hope of replacing cppo in OCaml static analysis tools. It encodes
version-dependent changes of the compiler internals in the type system, making
it safe and easy to integrate in existing codebases.

## First class modules (16h)

This work is available in
[PR #112](https://github.com/LexiFi/dead_code_analyzer/pull/112) and
[PR #117](https://github.com/LexiFi/dead_code_analyzer/pull/117).

First class modules are handled similarly to functor applicaitons: when a
module is packed into a value, then all the elements that are required by
the result are considered as used by requirement.
Prior to this work, module packing was not processed by the analyzer, leading
to false positives (observed on Opam, Frama-C and the Goblint analyzer).

Similarly to the type equivalence resolution, this relies on `Env.t` loading
which may impact performances.

An added bonus is the fixed support for methods in functor applications,
which were skipped instead of considered used by requirement.

This work is not part of any release yet.
